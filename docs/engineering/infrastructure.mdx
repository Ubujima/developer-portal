# Infrastructure

**Lean today. Controlled tomorrow. Scalable when needed.**

Ubujima's infrastructure strategy is designed around a simple principle:

> **Use the simplest infrastructure that reliably supports the product today while creating a practical path toward greater control tomorrow.**

We are intentionally avoiding unnecessary infrastructure complexity while AfroCom, Ma'at AI and Maji are still evolving.

Our infrastructure will grow progressively with the products, users, engineering team and operational requirements.

# 2. Infrastructure Philosophy

Our infrastructure decisions should prioritize:

### Reliability

Systems should remain available and recoverable.

### Security

Infrastructure must protect user data, credentials and platform services.

### Cost Efficiency

Infrastructure should be proportional to actual usage.

### Portability

Where practical, systems should avoid unnecessary dependence on a single infrastructure provider.

### Automation

Repeated operational tasks should increasingly be automated.

### Observability

We should know when systems fail, degrade or behave unexpectedly.

### Simplicity

Complexity should be introduced only when it provides meaningful value.

4. Why We Use Managed Services
Managed services allow a small team to concentrate on product development instead of spending excessive time maintaining infrastructure.
For example, using Supabase currently reduces the amount of infrastructure we need to operate ourselves.
Similarly, Cloudinary provides media infrastructure that would otherwise require significant engineering and operational work.
Managed infrastructure is therefore not considered a temporary failure or architectural mistake.
It is a deliberate trade-off.
The question is:
When does owning the infrastructure create more value than using the managed service?

6. Criteria for Replacing a Managed Service
A managed service should only be replaced when there is a clear reason.
Potential reasons include:
Cost at scale
Performance limitations
Architectural limitations
Vendor dependency
Data control requirements
Custom functionality
Infrastructure requirements
Compliance requirements
Integration requirements
Strategic platform independence
The decision should consider both the technical benefit and the operational cost.
Owning infrastructure also means owning:
Maintenance
Security
Monitoring
Backups
Updates
Incident response
Scaling
Reliability
Therefore:
Self-hosting is not automatically better.

9. Coolify
Coolify is part of the current infrastructure toolkit and provides a practical way to deploy applications and services without immediately introducing significant infrastructure-management overhead.
It can support deployments such as:
Web applications
APIs
Backend services
Containers
Databases
Internal tools
As the platform grows, Coolify may continue to be used for appropriate workloads even as infrastructure becomes more sophisticated.
The goal is not to replace a useful tool simply because a larger infrastructure architecture is available.

10. Development Environments
Development should distinguish between:
Development
     │
     ▼
Testing / Staging
     │
     ▼
Production

Developers should avoid making changes directly to production systems unless explicitly authorized.
Each environment should use appropriate:
Configuration
Credentials
API keys
Databases
Storage
Logging
Access permissions
Production credentials must never be committed to source control.

11. Environment Variables and Secrets
Secrets must be treated as sensitive infrastructure assets.
Examples include:
Database credentials
API keys
Authentication secrets
Private keys
Cloudinary credentials
Payment credentials
AI provider keys
Deployment credentials
Never commit secrets into GitHub.
Do not place production credentials inside source code.
Use appropriate environment variables and secret-management mechanisms.
Example:
DATABASE_URL=...
API_KEY=...
JWT_SECRET=...

Actual production values should never appear in documentation or repositories.

13. Backups
Important data and infrastructure configuration must have appropriate backup strategies.
Backup planning should consider:
Database backups
Media
Configuration
Infrastructure configuration
Critical secrets recovery
Source code
Deployment configuration
Backups should not simply exist.
They should periodically be tested for restoration.
A backup that has never been restored is an assumption, not a recovery strategy.

14. Monitoring and Observability
As the number of services increases, observability becomes increasingly important.
We should progressively monitor:
Service availability
Response times
Error rates
Resource usage
Database health
Storage usage
API traffic
Authentication events
Deployment status
Security events
At minimum, production services should provide useful logs.
As the platform matures, centralized monitoring, metrics and distributed tracing may be introduced.

15. Infrastructure and Cost Management
Infrastructure spending should be monitored as a first-class engineering concern.
Every service introduces potential costs including:
Compute
Storage
Database
Bandwidth
Media delivery
AI inference
Third-party APIs
Monitoring
Backups
Developers should consider cost when designing systems.
For example:
If a feature can perform an operation once per day instead of once per second without affecting the user experience, the cheaper design may be the better design.
Cost optimization should not compromise security or reliability, but neither should infrastructure be over-engineered before demand exists.

16. Infrastructure as Code
As infrastructure becomes more complex, configuration should increasingly become reproducible.
Where appropriate, infrastructure should be represented through code or version-controlled configuration.
This allows:
Repeatable deployments
Easier recovery
Peer review
Change tracking
Environment consistency
The exact tooling will evolve with the infrastructure.

23. Infrastructure Principle
The infrastructure should evolve with the organization.
We do not need to own everything today.
We do need to ensure that today's decisions do not prevent us from owning or replacing critical components tomorrow.
The guiding principle is:
Managed when sensible. Self-controlled when valuable. Open where practical. Automated wherever possible.
Our infrastructure should enable developers to move quickly today while creating a reliable foundation for the larger Ubujima ecosystem of tomorrow.
